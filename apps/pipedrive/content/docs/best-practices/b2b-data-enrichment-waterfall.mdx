A waterfall should stop spending when it has a defensible answer, not when any provider returns a non-empty response. Design separate acceptance rules for work email, phone and company attributes. Otherwise a weak email can terminate the whole process while an unrelated company field silently replaces a trusted value in Pipedrive.

Source: [Deepline B2B enrichment waterfall guide](https://deepline.com/docs/guides/b2b-data-enrichment-waterfall). Source read date: **2026-10-18**. This original offline implementation plan includes **no live Pipedrive execution** or provider requests. It contains no copied source commands or code.

## Deepline-specific guidance versus this Pipedrive adaptation

The source describes declared provider sequences, validation, provenance and cost per usable output. Its provider connectors and Play execution are Deepline-specific. The Pipedrive adaptation treats that orchestration as an external service and publishes only approved fields to persons or organisations. No native Pipedrive waterfall, provider billing arrangement or automatic conflict protection is implied.

Pipedrive’s [Persons API](https://developers.pipedrive.com/docs/api/v1/Persons) documents person IDs, `owner_id`, `org_id`, and `emails`/`phones` arrays. A person is a contact, not a Pipedrive user. Treat employer linkage, primary-address selection and field updates as separately reviewed decisions; retain the existing organisation unless a linkage change is explicitly approved. Pipedrive’s [Organizations API](https://developers.pipedrive.com/docs/api/v1/Organizations) documents organisation IDs, `name`, `website`, `owner_id` and updates. People are [persons](https://developers.pipedrive.com/docs/api/v1/Persons) linked by `org_id`; [deals](https://developers.pipedrive.com/docs/api/v1/Deals) carry their own `person_id`, `org_id`, `owner_id`, `pipeline_id` and `stage_id`. These record links do not prove legal-entity identity or authorise reassignment.

All `ops_` names in this guide are proposed display labels or external-ledger columns, not literal Pipedrive API keys. Resolve each approved field against the account’s [custom-field metadata](https://pipedrive.readme.io/docs/core-api-concepts-custom-fields), validate its type and option IDs, and map it to its account-specific 40-character hash. For the v2 person, organisation and deal endpoints, send mapped values inside `custom_fields`; never send an `ops_` label as a top-level payload key. Deepline integrations mentioned by the source are documented upstream, not installed or executed here. Pipedrive references were reviewed on **2026-10-20**.

## Prerequisites and licensing

Choose one cohort, required outputs and maximum cost per attempt. Secure provider usage rights and approve the credential owner, fallback providers and permissible geographies. Reserve a fixed holdout sample to compare providers without changing the scoring rubric after seeing results.

Use an authorised export and review-first proposals as the baseline. Before a later integration, verify the actual Pipedrive permissions, field capacity and selected API contracts; API access, automation access, Campaigns access and provider rights are separate. This design requires no native scoring engine, custom-code workflow action or Pipedrive CLI. It does not assume that an account has any paid automation or enrichment feature.

## Implementation steps

1. **Resolve identity before lookup.** Carry the Pipedrive object type and record ID for every input. Associate a contact with a company only through an independently accepted relationship, not a name string copied into a text field. For ambiguous or new identities, keep a staged proposal rather than automatically creating contact and company pairs.
2. **Declare a field matrix.** Work email requires person/employer agreement and acceptable mailbox evidence; phone requires a documented number type and country context; employee data requires entity scope and a stated count or range definition. Define source age limits per field. Passing one field must not imply that every field in the provider response is accepted.
3. **Order providers using pilot evidence.** Rank them by accepted incremental coverage and full marginal cost for the chosen geography and field. Provider A can supply an accepted phone while Provider B is tried only for a missing work email. Keep the accepted field intact when a later provider disagrees about an unrelated attribute. Do not assume a vendor's aggregate coverage claim predicts your cohort.
4. **Keep a stage receipt.** Record input revision, stage name, request receipt, response state, candidate field, rejection reason, provider charge and acceptance-policy version. Proposed Pipedrive fields such as `ops_enrichment_state`, `ops_enrichment_checked_at` and `ops_enrichment_receipt_url` expose a summary; the external ledger retains field-level detail. Never store credentials or unrestricted sensitive payloads in CRM fields.
5. **Separate completion from publication.** A staged record can be lookup-complete but awaiting approval. Prepare a minimal future update containing only accepted, authorised fields. Reread the relevant person/organisation values, stop on a changed snapshot, and read back each field after publication. Handle associations independently. These are recommended writer controls, not claims of a multi-record transaction.

## Approval boundary and failure handling

No stage runs and no CRM write is authorised by this document. A later pilot needs approval of provider order, budget, fields, overwrite policy and cohort. Person creation, ownership, qualification and outreach remain separate. Accepted email evidence does not establish [Campaigns consent](https://support.pipedrive.com/en/article/campaigns-marketing-contacts).

Differentiate no data, invalid candidate, conflicting evidence, quota exhaustion and transient failure. Use bounded retries only where a new attempt can resolve an operational failure. Stop at the cost ceiling with a visible partial outcome instead of silently dropping rows. A rerun should resume unresolved fields from the same input revision, not charge every provider again. Reconcile an unknown write outcome by reading the destination first.

## Validation and economics

Use fixtures where different stages supply different fields, an early candidate is rejected, two providers disagree and a partial write fails. Verify that later stages do not run for an already accepted field, all costs remain attributed and unchanged destination values produce no writes. Reconcile every input to an accepted or explicit exception state. Report accepted fields and usable persons separately, counting a contact once and including retries and review effort in total cost. These are proposed tests and accounting rules; no real provider acceptance rate or live CRM behaviour is claimed.
