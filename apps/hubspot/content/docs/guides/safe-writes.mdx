---
title: Make every write deliberate
description: Freeze inputs, inspect a dry run, confirm the exact operation and reconcile the result.
---

Reading CRM data and changing it are separate permissions. A successful lookup does not authorise an update, and a user approving one company does not approve every company returned by a broader query.

This guide combines the HubSpot skills library's documented CLI safety flow with a conservative execution procedure. CLI behaviour is source-verified only: the skills repository is Markdown guidance, not the implementation of the installed binary.

## Establish the write boundary

Before preparing a payload, record the portal, object type, exact record IDs, fields being changed and the user's authorised purpose. Read the current schema and affected records. Resolve ambiguous identities first. For bulk work, collect all pages before calculating impact; a single search page can hide most of the cohort.

Save the proposed inputs to a stable, access-controlled JSONL file. Do not rebuild the cohort from a changing live query between preview and execution. This frozen-input rule is a recommended safeguard: the upstream example re-runs its search, while its prose requires the same input for confirmation.

## Understand the documented confirmation flow

The source says irreversible operations require a dry run, a digest and a confirmation value even for one row. It includes update, upsert, delete, merge, association removal and several metadata deletions in that class. Creation has different preview semantics; it still needs the owner's authority.

The following is the upstream **dry-run-only** example, not an instruction to delete subscribers:

```bash
hubspot objects search --type contacts --filter "lifecyclestage=subscriber" \
| jq -c '{id}' \
| hubspot objects delete --type contacts --dry-run \
| tee /tmp/preview.jsonl
```

Do not run that selection against a real portal merely to test the guide. For an authorised task, use a bounded, saved cohort and a durable review-file location rather than the example's temporary path.

## Read the preview rather than inventing it

Inspect the target portal, affected count, reversibility and command hint. Copy the digest and confirmation semantics from the actual preview; do not invent a digest or assume that confirmation is always a row count. The source documents a 300-second digest lifetime, but installed help and actual preview output remain authoritative.

If the input, portal or intended change differs from what was approved, stop and generate a new preview. An expired digest is a reason to re-preview, not to bypass a guard. The source says `--force` is deprecated and ignored.

Only the authorised execution step should add the returned digest and confirmation to the same input. This guide deliberately provides no ready-to-run destructive apply command.

## Verify individual results

A process exit alone does not establish that every record changed. The source describes one result per input row with `ok: true` or `ok: false`; reconcile IDs, requested values and failures, then read affected records back. Preserve unresolved rows separately. Do not replay a whole batch after an uncertain outcome, because some rows may already have succeeded.

For an audit:

```bash
hubspot history --since 1h --format table
```

This is a local audit log, not an undo command. The source explicitly says `history` does not restore records. Recovery depends on the operation and the CRM's supported interface.

## Keep publication separate

Never put contact values, portal exports, credentials or raw provider receipts into a public documentation site. In the sponsor example, the public packet exposes contact state rather than a usable route, and every outreach message remains a draft. See [seed-data mapping](/docs/guides/seed-data) for a public-safe model and [orchestration](/docs/guides/orchestration) for ownership rules across parallel work.
