Source: [Deepline CRM workflow automation](https://deepline.com/docs/guides/crm-workflow-automation). Source and HubSpot documentation read: 2026-10-18.

This is an offline implementation plan. No live HubSpot execution has taken place, and no records, workflows or permissions have been changed. The aim is to make a proposed update explainable before making it automatic: which record, which property, whose authority and what evidence would justify the change?

## Deepline-specific behaviour versus HubSpot adaptation

The Deepline guide describes an orchestration discipline: assign field ownership, prepare a change proposal, identify repeated work and verify the destination. It points to Deepline integrations and agent tooling, but their availability is not a HubSpot guarantee. This adaptation uses HubSpot contacts and companies as destinations and an external change ledger as the control plane. The ledger, conflict policy and approval states below are recommendations, not built-in HubSpot transaction features.

HubSpot documents property updates and record retrieval in its [contacts guide](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/contacts/guide) and [companies guide](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/companies/guide). Those operations are building blocks; they do not by themselves implement the proposed safety policy.

## Prerequisites and licensing

Obtain an administrator-approved integration with only the required object read and write scopes, a named RevOps operator and a non-production test destination where available. Inventory existing imports, integrations and workflows that touch the same fields. Keep credentials outside CRM properties and receipts.

Retrieve property definitions before designing the mapping. The [Properties API](https://developers.hubspot.com/docs/api-reference/legacy/crm/properties/guide) distinguishes internal names, data types, field types and enumeration options. Confirm account property limits and permissions before creating custom fields. Native workflow actions vary by subscription; HubSpot lists custom code under Data Hub Professional and Enterprise in [workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions). An external worker is an architectural alternative, not a way to unlock licensed HubSpot features.

## Model the change contract

Use a destination identity comprising account, object type and record ID. A contact and company can have the same numeric-looking ID, so never key the ledger on the ID alone. For each candidate field, store old value, proposed value, evidence reference, evidence time, input revision, workflow version, approver and final observed value.

For an initial company refresh, allow only a small approved set such as company description or industry candidates. Keep `hubspot_owner_id`, `lifecyclestage`, deal properties and customer-entered corrections outside that set. Proposed custom fields such as `ops_update_state` and `ops_update_receipt` are local design names that must be created and type-checked; they are not default properties. Do not use a contact's company-name text as proof of a contact-to-company association.

## Implementation steps

1. **Define the trigger and stop conditions.** Select a bounded cohort by a business rule, then snapshot its IDs and current values. Reject archived, unresolved or policy-excluded records before calling enrichment. Record why each exclusion happened so the cohort denominator remains meaningful.
2. **Prepare a property-level proposal.** Validate text length, numeric range and allowed enumeration values against the actual schema. Missing enrichment means no proposed write, not an empty string. HubSpot documents that an empty string can clear a property; accidental clearing must therefore be explicitly blocked.
3. **Evaluate precedence.** Preserve values supplied by an authorised account owner unless a documented rule permits replacement. Obtain a fresh record read immediately before applying an approved proposal. If the relevant value changed, withdraw the proposal and review the new state.
4. **Serialise competing work.** Use an external per-record or per-property lock for your own workers and nominate one writer across integrations. A read followed by an update is not an atomic compare-and-swap. If other writers cannot be controlled, use review instead of claiming conflict-free automation.
5. **Apply and reconcile separately.** Update only approved properties on the resolved ID, then retrieve those same properties directly. Read associations separately when they form part of the intended outcome; a successful property update does not demonstrate that the company relationship exists.

## Approval boundary

An administrator should approve the field allowlist, precedence policy, cohort and rollback plan before enabling any writes. Within that policy, a deterministic blank-field fill may be automated. Identity merges, owner changes, lifecycle movement and external communications require their own approval, even when enrichment suggests them. Changing a proposed receipt into an approved receipt must be attributable to an authorised person or previously approved deterministic rule.

## Failure handling

Separate invalid input, denied scope, stale proposal, transient provider failure and ambiguous destination outcome. Do not retry a schema error as if it were a network problem. Back off within the documented [API usage limits](https://developers.hubspot.com/docs/developer-tooling/platform/usage-guidelines), cap attempts and assign exhausted items to an operator. After a timeout following submission, read the destination and reconcile before another write. Rollback is a new, approved compensating update after checking for later human edits, not a blind restoration of the original snapshot.

## Validation and acceptance

Plan tests for an unchanged value, valid blank fill, protected field, conflicting human edit, repeated event, association failure and timeout after submission. A repeated event must reuse its receipt and avoid a second side effect. Accept only when read-back values match the approved proposal and protected fields remain unchanged. Report verified changes divided by proposed changes, with unresolved outcomes separately counted. These are acceptance criteria for a future pilot, not results from this authoring exercise.
