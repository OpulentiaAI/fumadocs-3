title: 'Review Apollo matches before preparing HubSpot contact updates'
description: 'Use an agent-assisted matching proposal to resolve people and employers, map fields and protect existing HubSpot relationships.'

Treat Apollo matching as a source of candidate evidence, not permission for an agent to rewrite HubSpot. A person can have a correct name and an outdated employer; a returned company can be the global parent rather than the account your sales team manages. The useful output is a reviewed identity decision plus a narrow set of proposed fields.

Source: [Deepline Apollo and Claude Code guide](https://deepline.com/docs/guides/apollo-claude-code). Source read date: **2026-10-18**. This original offline implementation plan includes **no live HubSpot execution**, Apollo requests or agent installation. Source commands and code are intentionally omitted because their licence has not been established.

## Deepline-specific guidance versus this HubSpot adaptation

The source describes Deepline's CLI/MCP surfaces, checked Plays, Apollo People Match access and declared fallback stages. Those are Deepline execution arrangements, not HubSpot-native functions. Provider access, returned fields and billing remain dependent on the current Apollo and Deepline contracts; this guide does not independently verify those commercial claims.

The HubSpot adaptation starts after a candidate match is returned. It prepares a contact update and an independently reviewed contact-to-company relationship. HubSpot documents contact fields, record-ID retrieval, associations and update operations in the [Contacts API guide](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/contacts/guide).

## Prerequisites and licensing

Obtain an authorised input sample containing HubSpot contact IDs where available, original names, employer evidence and any approved email input. Agree provider rights for lookup, storage and downstream use. Keep provider credentials in an approved secret store; neither prompts nor CRM properties should contain raw keys. A coding assistant's ability to call a tool is not business approval to spend provider credits or write CRM data.

Review the portal's [contact property metadata](https://developers.hubspot.com/docs/api-reference/latest/crm/properties/guide), integration scopes and schema-creation permissions. This plan assumes no native enrichment subscription or agent capability in HubSpot. If a native workflow will consume accepted results, check its [subscription, permission and action requirements](https://knowledge.hubspot.com/workflows/create-workflows) separately. Ordinary contact/company associations do not require inventing custom labels; any label feature needs its own entitlement review.

## Implementation steps

1. **Create an input identity contract.** Carry contact object type and record ID alongside the raw submitted values. Separate names from company identifiers. For contacts without a known CRM ID, collect candidate matches in a review file instead of immediately creating records. Deduplicate the input before provider calls so one person does not incur repeated lookup cost.
2. **Review person and organisation separately.** Compare the candidate's person evidence, current role and employer with the intended record. A name-only match is insufficient when two people are plausible. Resolve the candidate employer against HubSpot `name`, `domain` and the existing company ID using the [company model](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/companies/guide). Retain a rejected-parent explanation when the operating subsidiary is required.
3. **Map fields without changing their meaning.** Propose verified values for `jobtitle` or `phone` only when the provider's definition fits the destination. Put candidate email, match state and source receipt into proposed staging fields such as `ops_candidate_email`, `ops_match_state` and `ops_match_receipt_url`. Do not replace the primary `email` during matching simply because a provider returned another address.
4. **Prepare associations explicitly.** Record whether the existing contact/company association should remain, be supplemented or enter review. Inspect the actual association direction and type rather than borrowing an example identifier from documentation. A current job match does not prove every historic deal should be associated with the new employer.
5. **Separate review from write preparation.** Produce old value, candidate value, evidence, reviewer decision and input revision for each field. A future writer rereads the contact and employer relationship, rejects changed snapshots, submits only approved changes and reads back each affected record. The single-writer rule and conflict check are proposed controls, not automatic guarantees provided by Apollo or HubSpot.

## Approval boundary and failure handling

The offline plan authorises no provider spend, contact creation, association changes or outreach. Before a pilot, approve its rows, provider budget, permitted fields and reviewer. Marketing consent must not be inferred from a matched address: HubSpot's [marketing email permission policy](https://knowledge.hubspot.com/marketing-email/understand-opt-in-consent-for-email) states that enrichment-derived addresses alone do not meet its consent requirements.

Distinguish no match, stale employer, conflicting person, quota failure and temporary outage. Only the last two are operational retries, subject to limits. A fallback provider must not erase contrary evidence. If an update outcome is unknown, inspect the CRM record before retrying; avoid replaying a create operation that may already have succeeded.

## Validation and acceptance

Use authorised test fixtures for duplicate rows, common names, changed employers, personal addresses, missing domains and a parent/subsidiary pair. Confirm that accepted person matches do not automatically imply accepted email or company associations. Test replay against the same input revision and verify no duplicate contacts or unintended relationship changes. Measure reviewed usable contacts per total lookup cost, not provider response count. These checks are proposed; no match accuracy, live integration or delivery behaviour has been verified here.
