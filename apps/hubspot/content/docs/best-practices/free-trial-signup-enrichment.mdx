Source: [Deepline trial signup enrichment](https://deepline.com/docs/guides/free-trial-signup-enrichment). Source and HubSpot documentation read: 2026-10-18.

This offline implementation plan has had no live HubSpot execution. A valid signup should reach the product even when optional enrichment is slow or unavailable. The CRM handoff is a recoverable downstream process, not a condition for creating the user's account.

## Deepline-specific behaviour versus HubSpot adaptation

The source separates the saved signup event from company lookup and later lifecycle decisions. It describes an input-revision example in which a user's company correction must survive an older result. Deepline discovery and enrichment actions belong to its tooling. This adaptation retains that event discipline but proposes HubSpot contacts, companies and explicit associations as the destination. The queue, revision checks and handoff ledger are recommended application controls, not automatically supplied by HubSpot.

The [HubSpot contacts guide](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/contacts/guide) documents retrieving contacts by record ID or email and updating properties. Resolve an existing contact first; do not create a second person merely because an optional company lookup failed.

## Prerequisites and licensing

The product must durably store a signup event ID, product user ID, event time and the submitted identity before starting optional work. Agree privacy notices, retention and provider use with the appropriate owner. Secure a scoped integration, an exception queue and a service responsible for reconciling handoffs.

Check HubSpot property capacity and permissions. The design can use an external queue without custom objects. Native custom code requires Data Hub Professional or Enterprise according to [workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions). Native workflow availability and any later sequence features must be verified independently; creating a trial contact is not licence or consent to enrol that person in sales outreach.

## Define the record model

Use the product user ID for the stable person mapping and retain the HubSpot contact ID once resolved. A proposed custom unique property, `ops_product_user_id`, can support this mapping if created and tested. The [Properties API](https://developers.hubspot.com/docs/api-reference/legacy/crm/properties/guide) documents unique identifier properties; uniqueness on the contact does not replace an event ledger for multiple signups or deliveries.

Suggested custom properties include `ops_trial_started_at`, `ops_signup_input_revision`, `ops_company_match_state` and `ops_trial_evidence_reference`. They are proposed names, not default fields. Store product activity separately from enrichment status. For companies, retain record ID, normalised domain and match evidence. A free-mail address does not establish the mailbox provider as the user's employer. A consultant may legitimately use one domain while evaluating for another organisation.

## Implementation steps

1. **Acknowledge the signup independently.** Commit the product account and event, then enqueue optional enrichment. The product response should not wait for a provider or HubSpot. Record pending state without presenting inferred company details as user-confirmed facts.
2. **Resolve the existing contact.** Use a saved HubSpot ID where available, then the approved product-ID or email match policy. Review contradictory identities instead of merging automatically. HubSpot documents constraints for contact upserts, including limitations when email is used; do not assume every partial upsert is supported.
3. **Find the company candidate.** Use a work domain only when appropriate, and preserve user-entered company corrections. Create or link a company only after the acceptance policy passes. The [companies guide](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/companies/guide) and [associations guide](https://developers.hubspot.com/docs/api-reference/latest/crm/associations/associate-records/guide) cover the distinct record and relationship operations.
4. **Compare revisions at application time.** If a user corrects the company while revision one is processing, retain the late result against revision one but do not apply it over revision two. Queue a new lookup only for the current revision. User-supplied and inferred values should remain distinguishable.
5. **Stage and verify the handoff.** Propose only the approved trial and evidence fields. After an authorised update, retrieve the contact and inspect the intended company association. Keep the event-to-contact mapping and resulting IDs so repeated delivery reconciles existing work rather than recreating it.

## Approval boundary

Approve the identity policy, property mapping and rules for company creation before enabling writes. Keep `lifecyclestage`, `hubspot_owner_id`, lead scoring and communications outside this enrichment step. Successful company matching is not proof of qualification. A later sales handoff must evaluate current account status, suppression and eligibility under its own approved policy.

## Failure handling

On provider failure, preserve the signup and an explicit unresolved or provider-error state. Do not score unknown company data as poor fit. On a timeout after a CRM write, read and reconcile the saved destination before repeating the operation. If a contact exists but company association fails, mark a partial handoff and repair only the relationship. Never make the user repeat signup to repair internal integration state.

## Validation and acceptance

Plan fixtures for a work email, personal email, existing contact, repeated event, changed company, slow provider and CRM permission failure. For every permitted signup, onboarding must complete independently. The revised company must survive stale callbacks, and retries must not duplicate contacts or associations. Track enrichment latency, accepted matches, unresolved cases and handoff repair age separately from activation. Any later conversion analysis must avoid attributing causality to enrichment without an appropriate experiment.
