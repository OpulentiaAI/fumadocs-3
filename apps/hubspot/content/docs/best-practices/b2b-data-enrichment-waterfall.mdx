title: 'Build a field-level enrichment waterfall for HubSpot'
description: 'Plan provider order, stopping rules, per-field evidence and controlled CRM write-back without confusing coverage with quality.'
---

A waterfall should stop spending when it has a defensible answer, not when any provider returns a non-empty response. Design separate acceptance rules for work email, phone and company attributes. Otherwise a weak email can terminate the whole process while an unrelated company field silently replaces a trusted value in HubSpot.

Source: [Deepline B2B enrichment waterfall guide](https://deepline.com/docs/guides/b2b-data-enrichment-waterfall). Source read date: **2026-10-18**. This original offline implementation plan includes **no live HubSpot execution** or provider requests. It contains no copied source commands or code.

## Deepline-specific guidance versus this HubSpot adaptation

The source describes declared provider sequences, validation, provenance and cost per usable output. Its provider connectors and Play execution are Deepline-specific. The HubSpot adaptation treats that orchestration as an external service and publishes only approved fields to contacts or companies. No native HubSpot waterfall, provider billing arrangement or automatic conflict protection is implied.

HubSpot's [Contacts API](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/contacts/guide) and [Companies API](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/companies/guide) document the destination records and associations. Their support for updating properties does not validate provider content.

## Prerequisites and licensing

Choose one cohort, required outputs and maximum cost per attempt. Secure provider usage rights and approve the credential owner, fallback providers and permissible geographies. Reserve a fixed holdout sample to compare providers without changing the scoring rubric after seeing results.

Inspect destination schemas with the [Properties API](https://developers.hubspot.com/docs/api-reference/latest/crm/properties/guide). This plan uses ordinary contacts and companies plus proposed custom operational properties; it does not require custom objects. If native workflows consume the accepted cohort, check the [qualifying subscription and individual action availability](https://knowledge.hubspot.com/workflows/create-workflows). API access, workflow entitlement, provider credits and data-use rights are four different prerequisites.

## Implementation steps

1. **Resolve identity before lookup.** Carry the HubSpot object type and record ID for every input. Associate a contact with a company only through an independently accepted relationship, not a name string copied into a text property. For ambiguous or new identities, keep a staged proposal rather than automatically creating contact and company pairs.
2. **Declare a field matrix.** Work email requires person/employer agreement and acceptable mailbox evidence; phone requires a documented number type and country context; employee data requires entity scope and a stated count or range definition. Define source age limits per field. Passing one field must not imply that every field in the provider response is accepted.
3. **Order providers using pilot evidence.** Rank them by accepted incremental coverage and full marginal cost for the chosen geography and field. Provider A can supply an accepted phone while Provider B is tried only for a missing work email. Keep the accepted field intact when a later provider disagrees about an unrelated attribute. Do not assume a vendor's aggregate coverage claim predicts your cohort.
4. **Keep a stage receipt.** Record input revision, stage name, request receipt, response state, candidate field, rejection reason, provider charge and acceptance-policy version. Proposed HubSpot fields such as `ops_enrichment_state`, `ops_enrichment_checked_at` and `ops_enrichment_receipt_url` expose a summary; the external ledger retains field-level detail. Never store credentials or unrestricted sensitive payloads in CRM properties.
5. **Separate completion from publication.** A staged record can be lookup-complete but awaiting approval. Prepare a minimal future update containing only accepted, authorised fields. Reread the relevant contact/company values, stop on a changed snapshot, and read back each property after publication. Handle associations independently. These are recommended writer controls, not claims of a multi-record transaction.

## Approval boundary and failure handling

No stage runs and no CRM write is authorised by this document. A later pilot needs approval of provider order, budget, destination fields, overwrite policy and cohort. Contact creation, owner changes, lifecycle transitions and outbound enrolment remain separate. An accepted email does not establish [HubSpot marketing consent](https://knowledge.hubspot.com/marketing-email/understand-opt-in-consent-for-email).

Differentiate no data, invalid candidate, conflicting evidence, quota exhaustion and transient failure. Use bounded retries only where a new attempt can resolve an operational failure. Stop at the cost ceiling with a visible partial outcome instead of silently dropping rows. A rerun should resume unresolved fields from the same input revision, not charge every provider again. Reconcile an unknown write outcome by reading the destination first.

## Validation and economics

Use fixtures where different stages supply different fields, an early candidate is rejected, two providers disagree and a partial write fails. Verify that later stages do not run for an already accepted field, all costs remain attributed and unchanged destination values produce no writes. Reconcile every input to an accepted or explicit exception state. Report accepted fields and usable contacts separately, counting a contact once and including retries and review effort in total cost. These are proposed tests and accounting rules; no real provider acceptance rate or live CRM behaviour is claimed.
