Source: [Deepline enrichment API guide](https://deepline.com/docs/guides/enrichment-api). Source and HubSpot documentation read: 2026-10-18.

This offline implementation plan includes no live HubSpot execution. The service described here should return a validated enrichment proposal and a traceable receipt before it is allowed to modify a CRM record. A provider response and a successful CRM handoff are different outcomes.

## Deepline-specific behaviour versus HubSpot adaptation

The Deepline source recommends stable request identity, provider fallbacks and explicit acceptance rules. Its orchestration and provider access are Deepline-specific. This adaptation proposes an external enrichment service connected to HubSpot contacts and companies. Its request envelope, state machine, locks and cost ledger are design recommendations, not documented HubSpot APIs.

HubSpot documents reading and updating contacts in the [contacts API guide](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/contacts/guide), while its [companies guide](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/companies/guide) covers the company destination. Select and pin the API version used by your implementation. Do not mix a versioned search endpoint with a copied legacy request path without checking the relevant contract.

## Prerequisites and licensing

Require an approved provider agreement, a restricted service credential, a durable queue, secret storage and an operator who owns exceptions. Retrieve HubSpot property definitions and confirm object scopes before building the mapping. Request only the objects and fields needed for the first use case; avoid broad write authority for a service that initially produces proposals.

HubSpot's [workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions) lists custom code for Data Hub Professional and Enterprise. Hosting the service outside HubSpot is a valid design alternative, but does not grant access to unlicensed native actions. Verify account-specific custom-property capacity and API limits before sizing the job. No custom object or HubSpot-native event store is assumed here.

## Define the request and result contracts

Each request should carry tenant identity, object type, HubSpot record ID when known, business request ID, input revision, required fields and policy version. Keep a person's submitted email separate from a company's normalised domain. A free-mail domain is not an employer identifier. Retain the raw submitted value alongside the normalised lookup value without exposing it in operational logs.

Return field-level candidates with source, observation time, match evidence and one of accepted, missing, invalid, conflicting or provider-error. These proposed statuses must not collapse into a single Boolean. An accepted company industry can coexist with an unresolved contact phone. Keep the write-back status independent so a good enrichment result remains usable when CRM permissions fail.

Recommended HubSpot custom fields such as `ops_enrichment_state`, `ops_enrichment_checked_at` and `ops_enrichment_receipt` are implementation names, not built-ins. Check their types using the [Properties API](https://developers.hubspot.com/docs/api-reference/legacy/crm/properties/guide); preserve default `lifecyclestage` and `hubspot_owner_id` outside the enrichment payload.

## Implementation steps

1. **Resolve identity before spending.** Read the known CRM ID directly. When matching is necessary, search for candidates and require decisive evidence. An empty search immediately after creation is not proof of absence: HubSpot's [CRM Search documentation](https://developers.hubspot.com/docs/api-reference/latest/crm/search-the-crm) notes indexing delay.
2. **Deduplicate work externally.** Persist a request record before calling a provider. Key it by tenant, target, input revision, field set and policy version. The same business request should return or reconcile the existing result rather than restarting a billable waterfall.
3. **Validate each provider response.** Check required fields, expected types, country context and contradictory identity evidence. Continue to another approved provider only for a defined unresolved need, and stop once that need is satisfied. A non-empty response is not sufficient acceptance.
4. **Stage the HubSpot proposal.** Map accepted fields to internal names and enumeration values. Do not clear existing values for missing provider data. Inspect contact-company associations separately; a text company name does not establish a CRM relationship, and object batch reads do not return associations.
5. **Apply only an approved field set.** Re-read current values and reject stale proposals. Serialise your own workers rather than claiming that read-before-write provides atomic conflict protection. Retrieve the target after the update and persist observed values in the receipt.

## Approval boundary

Approve provider routes, costs, retention and deterministic field-fill policies before any automated execution. Require review for ambiguous identities, changed company associations and overwrites of human-maintained values. Owner assignment, lifecycle movement, merges and outbound communication must remain separate operations. The enrichment API should not silently become a general-purpose CRM administrator.

## Failure handling

Distinguish rate limiting from bad input and denied access. Use bounded backoff for genuinely retryable failures and follow [HubSpot usage guidelines](https://developers.hubspot.com/docs/developer-tooling/platform/usage-guidelines) for the chosen app type. A timeout after a CRM update is an unknown outcome: read and reconcile before retrying. Record partial batch results per record, preserve successful work and send exhausted items to a repair queue with their request and destination IDs.

## Validation and acceptance

Plan contract tests for missing identifiers, duplicate requests, provider schema drift, conflicting candidates, an invalid HubSpot enumeration, permission loss and a timeout after submission. Verify that duplicate delivery cannot create a second record or repeat an accepted provider request unnecessarily. Accept a handoff only after destination read-back, with association checks when required. Evaluate accepted useful fields per total provider, platform and repair cost, keeping retries visible. These are future pilot requirements, not measured production performance.
