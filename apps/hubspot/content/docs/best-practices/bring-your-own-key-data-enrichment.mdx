---
title: 'Govern bring-your-own-key enrichment around HubSpot'
description: 'Separate provider credentials, HubSpot authorisation, data rights and accepted-output costs in an auditable enrichment design.'
---

Bringing an existing provider key into an enrichment workflow changes who pays and who controls access; it does not remove operational or legal responsibility. The safest design keeps credentials outside HubSpot, assigns a provider owner and publishes only approved data. Treat HubSpot authorisation and provider authorisation as independent capabilities with different scopes and failure modes.

Source: [Deepline bring-your-own-key enrichment guide](https://deepline.com/docs/guides/bring-your-own-key-data-enrichment). Source read date: **2026-10-18**. This is an original offline implementation plan with **no live HubSpot execution**, credential changes or provider calls. No real keys are required to review it.

## Deepline-specific guidance versus this HubSpot adaptation

The source explains central credential ownership, provider-specific routing, contract rights and complete workflow economics. Its managed/BYOK execution and commercial arrangements are Deepline-specific. Do not generalise a source pricing statement to HubSpot or assume every provider permits the same onward use.

This HubSpot adaptation recommends an external credential-owning worker and a separate CRM publication identity. Contacts and companies remain ordinary destination records under the [Contacts](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/contacts/guide) and [Companies](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/companies/guide) APIs. The governance registry is not represented as a CRM secret vault.

## Prerequisites and licensing

Prepare a provider registry containing contract owner, approved use, fields, geography, retention obligations, billing unit, quota, renewal and revocation contact. Legal or procurement review must determine permitted storage and sharing; successful API access cannot settle those rights. Identify the person authorised to approve spend beyond an agreed pilot ceiling.

A future CRM integration needs suitable object permissions and narrowly scoped authorisation. An administrator must inspect actual property definitions using the [Properties API guide](https://developers.hubspot.com/docs/api-reference/latest/crm/properties/guide). If HubSpot workflows are part of the route, verify a [qualifying subscription and each selected action](https://knowledge.hubspot.com/workflows/create-workflows); custom-code execution is not assumed. An external worker plus a reviewed file is the fallback when those capabilities are unavailable. Provider contracts and charges remain independent of HubSpot subscription fees.

## Implementation steps

1. **Draw the credential boundary.** The worker requests a provider capability from an approved secret manager; operators see a reference and owner, never a raw key. Maintain separate development and production authorisations where supported. Keep credentials out of prompts, request examples, exception messages, company properties and exported CSV files.
2. **Define the CRM data boundary.** Resolve contacts and companies using object type and HubSpot record ID. Read only fields needed for the approved enrichment purpose. Proposed operational fields may include `ops_enrichment_provider`, `ops_enrichment_state`, `ops_enrichment_checked_at` and `ops_enrichment_receipt_url`. Store a contract reference and non-sensitive receipt ID, not the key, billing credential or entire provider agreement.
3. **Route by field and rights.** Choose a provider only when the registry permits the requested field, territory and destination use. An available key is insufficient if a contract prohibits that storage or use. Preserve associated company IDs for contact employer checks, but do not alter relationships merely because a different provider names another organisation.
4. **Meter the complete attempt.** Attribute provider charges, retries, orchestration and reviewer effort to an input revision. Keep accepted fields separate from returned fields. When a provider charges per request and another per successful lookup, normalise the comparison to total cost per accepted business output rather than comparing unlike invoice line items.
5. **Prepare a controlled write boundary.** The CRM writer accepts only reviewed field proposals with source receipt, original destination value and policy version. Recheck the record before any later update and verify the observed values afterwards. Provider credential rotation must not silently expand the destination field list or change approved data sources. The single-writer arrangement is a recommendation, not a HubSpot-enforced field ownership feature.

## Approval boundary and failure handling

This plan authorises no credential creation, key rotation, provider spend or CRM writes. A later pilot needs approval for provider contract use, budget, sample, fields and overwrite rules. Merges, owner reassignment, lifecycle changes, association changes and communication remain excluded.

When a key is revoked or quota is exhausted, mark an operational hold and notify the provider owner. Do not fall back to an operator's personal key or an unapproved managed route. Rotation should preserve receipt attribution to the old non-secret credential reference while future requests use the replacement. If sensitive data appears in a log, stop distribution and follow the organisation's incident process; do not copy the leaked value into the CRM repair ticket.

## Validation and acceptance

Test with dummy credential references, denied provider rights, an exhausted budget, revoked access and a provider outage. Confirm that error outputs contain no secrets and that a failure on one provider cannot expand CRM privileges. Reconcile usage receipts to the approved sample and accepted field counts. Review whether retained data can be located for contract termination or deletion obligations. These are proposed tests, not verification of any provider, HubSpot account or secret-management system. The economic decision should use complete accepted-output cost, and may favour a managed route when direct-key operations cost more.
