---
title: 'Validate CSV inputs before a HubSpot import'
description: 'Design an identity-aware validation gate for HubSpot contacts, companies and associations with reconciled row dispositions and safe import approval.'
---

A file can be valid CSV and still be dangerous to import. A correctly quoted row might identify the wrong contact, map a company ID into a contact column or clear a field that sales owns. A useful preflight gate checks structure, identity and destination policy before enrichment or CRM changes begin. It preserves rejected rows rather than making them disappear from the denominator.

Source: [Deepline incoming CSV validation](https://deepline.com/docs/guides/validate-incoming-csv-files). Read date: **2026-10-18**. This is an original offline implementation plan; **no live HubSpot execution** or CRM import has been performed. Source licensing has not been established; source prose and code are not reproduced.

## Deepline-specific context vs HubSpot adaptation

The source separates file-level failures from row-level outcomes and demonstrates why duplicate source identities must be detected across the complete file. Its enrichment workflow references describe a possible next stage, not a requirement to call Deepline during validation.

This adaptation maps that boundary onto HubSpot contacts, companies and their associations. The accepted export is an import proposal, not permission to import. The local dispositions and provenance columns below are proposed validation metadata, not native HubSpot import statuses.

## Prerequisites and licensing

Agree on whether this is create-only, update-only or a mixed import, which objects are involved, which fields may change and whether partial processing is permitted. Have the portal administrator confirm import permissions and the precise import capabilities available in the account. API-based preflight lookup additionally needs the relevant read scopes. No custom object or paid workflow is required for a local validator; richer association labels and automation features have separate subscription requirements. [HubSpot's object guidance](https://knowledge.hubspot.com/records/understand-objects) identifies association labels as a Professional or Enterprise feature.

Read [HubSpot's import-file specification](https://knowledge.hubspot.com/import-and-export/set-up-your-import-file) before preparing the destination file. It requires a unique identifier when updating records and describes Record ID, contact Email and Company domain name as identification options. When importing several objects, use distinct headers such as Record ID - Contacts and Record ID - Companies. Never infer that an identifier has the same meaning across object types.

## Record and property mapping

Create a mapping specification for the contact properties `email`, `firstname` and `lastname`, and the company properties `name` and `domain` only if those fields are in scope. Verify property internal names and permitted values rather than translating visible labels into API names by guesswork; [the properties guide](https://developers.hubspot.com/docs/api-reference/legacy/crm/properties/guide) documents property types and metadata.

Proposed local-only columns are `source_record_id`, `source_file_revision`, `validation_disposition` and `validation_reason`. Do not import these automatically. If the organisation wants a CRM source-system ID, a separately reviewed custom property must be created first; that name is proposed, not built-in. Keep an external mapping between source IDs and HubSpot record IDs for reliable later reconciliation.

## Practical implementation steps

1. **Preserve the original.** Record the file checksum, declared encoding, source owner and export timestamp. Parse with a CSV-aware library that supports quoted commas, escaped quotes and embedded line breaks. Do not use physical line numbers as persistent record identity.
2. **Validate the complete header.** Reject the file for duplicate headers, missing required identity columns or ambiguous object mappings. Decide how a byte-order mark and empty lines are handled. A broken schema should not produce a partially trusted accepted file.
3. **Group identities before release.** Detect repeated source IDs across the entire revision. If two rows with one source ID disagree on the company, hold both. Otherwise an early row can escape before a later conflicting row is discovered.
4. **Resolve destination identity.** For update-only work, require a known HubSpot ID of the intended object and compare supplied evidence. Do not let an unresolved ID fall back silently to create. Contact email and company domain matching need conflict rules, especially where companies share a domain.
5. **Evaluate field policy.** Separate malformed values, stale observations and missing optional data. An empty phone is acceptable when phone enrichment is the next task. Define whether blanks mean no change or intentional clearing; never leave that interpretation to chance.
6. **Validate associations independently.** A row containing a contact and a company must resolve both identities before proposing their relationship. If association labels are used, confirm the account's configured labels and the intended direction rather than reusing another portal's IDs.
7. **Produce separate outputs.** Write accepted rows, exceptions and a receipt containing the contract version, input checksum and counts. Give every input record exactly one outcome: accepted, rejected, review or dependency error. Formula-like untrusted cells need a safe spreadsheet-display derivative; do not mutate canonical values in a way that changes CRM identity.

## Approval boundary

Parsing, normalisation and read-only identity checks can run under an approved data-handling policy. A reviewer must approve the final mapping, create/update mode, blank-value semantics and accepted subset before a live import. Record merges, owner changes, lifecycle changes and outreach enrolment are outside this gate. Passing an email syntax check does not verify mailbox reachability or authorise contact.

## Failure handling

Fail the whole file when structure is ambiguous; quarantine isolated row faults only if partial processing is authorised. Distinguish unavailable HubSpot lookups from absent records. Keep the original values and actionable reason codes in exceptions. After an uncertain future import outcome, inspect the import result and known record IDs before resubmitting: replaying a create-capable file can create duplicates.

## Validation and release criteria

Test a quoted company name, multiline note, duplicate header, conflicting duplicate source ID, swapped object IDs and optional blank phone. Assert that structural faults release no accepted rows. Reconcile input count to every disposition and verify that no rejected row enters the import proposal. In a future controlled pilot, read back updated properties and contact-company associations against the approved proposal, then repeat the same update-only file and confirm stable record counts. No such live pilot has been executed here.
